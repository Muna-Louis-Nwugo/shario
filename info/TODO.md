- [x] **Parent lookup only matches on bare `id`** (`check_line`, the `parent_col` projection lookup) — both do `element.0 == parent_id` with no peer check. If two peers' local counters collide on the same id, this silently resolves to whichever node comes first and anchors the whole sibling walk to the wrong parent. Needs `parent_id` to travel everywhere as `(IdSize, PeerIdSize)`, not a bare id — `Line`'s parent field needs a `parent_peer` slot too, and `add_crdt`/`Entry::add_crdt` need a `parent_peer` param threaded through. A remote op carries `coordinates` captured on the sender's replica; if a concurrent edit earlier in that line has already landed locally by the time the op is applied, the index has shifted and `coordinates` now points at the wrong element. Local/sequential use (the IDE handing back the position of a parent it just tracked itself) is fine and doesn't need this. This is structural, not cosmetic — needs `parent_id`/`parent_peer` to be resolved to a live position on the receiving replica (id → position lookup) rather than trusting a foreign `(line, col)` directly. Right now `add_crdt`/`find_crdt`/`find_tombstone` all assume the parent already exists locally. Planned fix: a "pending" set — an op whose parent is missing gets held there instead of applied; every time a *new* op is successfully applied, check the pending set for anything waiting on it and re-attempt those. Purely a network/queue concern, not `SharFile`'s — do this once `SharQueue` actually exists and drains.

Verified with two real processes whose shar directories have completely unrelated names, not just differing parent paths.

- [ ] **Tie-breaking needs to happen exclusively in the shar, not be replicated/guessed by IDE clients** — a plugin that wants to correctly render a remote peer's concurrent insert (`shario-vscode`'s `siblingInsertIndex`) currently has to reimplement `tree.rs`'s own sibling tie-break rule independently (larger id first, smaller peer breaks a tie on equal ids), comparing the incoming op's parent against each existing sibling's own parent reference. A network op arriving in that window correctly gets backlogged (its parent can't resolve against the still-empty default directory) — but `QueueWrap::new`'s `*guard = real_queue;` replaces the *entire* queue struct, backlog included, the instant the real directory loads.   - **Deeper than it first looked, confirmed via a real GitHub Actions run against a genuinely separate peer**: `(0, 0)` is `tree.rs`'s root sentinel, seeded directly into `self.characters` by `SharFile::add_file` at directory-load time — never routed through `add_network_operation_inner`. `network_backlog` only ever gets drained for a given `(id, peer)` key via `clear_network_backlog`, which exclusively fires from that function's own success branch (`queue.rs:341`). ## 🟡 Data model — decide before building more on top

- [x] **Reconsider `HashMap<LineSize, Line>` keyed by ordinal** (`src/shar/core/tree.rs:35`) — newline insert/delete renumbers every later key (O(n)) and concurrent line inserts collide. Decided direction: split into two structures instead of one —
  - `tree`: a single `HashMap<(IdSize, PeerIdSize), Node>` — no ordinal/line keying, no per-line partitioning. This is the actual CRDT state; the shar itself doesn't care about order, so parent lookup by id is O(1) instead of the current line-scoped forward/backward line search. Each `Node` holds `value`/`parent_id`/`parent_peer` plus a child/sibling pointer (ordered list of children, or next-sibling) so that finding a node's siblings for the insert tie-break doesn't require scanning every node for a matching `parent_id`.
  - `projection: Vec<Vec<(IdSize, PeerIdSize)>>`: a line/column → node-id index, purely derived from `tree` by walking child pointers from the root, never merged over the network. This is what the IDE actually consumes, since it works on positions, not ids. `add_crdt` patches it incrementally in the same call that mutates `tree` (no separate eventing layer needed since ownership is already a direct call chain: `SharQueue` → `SharDirectory` → `SharFile`).
  - Column lookup within a line still walks the small `projection` row directly — no fancier index needed at that scale.
- [ ] **`find_crdt`'s ring search cost, confirmed as the cause of intermittent multi-second socket-mode benchmark runs** (`src/shar/core/tree.rs`) — added a `ring_search_diagnostics()` counter (calls/total distance/max distance) to check instead of guessing. A clean automerge-paper run: mean distance ~1.4, max 48. A slow run (8-10s instead of ~3s): mean climbing past 281, max 1000+, and still climbing when sampled. Cause: socketioxide spawns each socket event as an independent tokio task with no ordering guarantee (confirmed via its source, not assumed), so the *server's* processing order can diverge from the client's send order under a burst — and since `line_hint` is computed by the client assuming its own order, a hint can end up far from the real position. Considered scrapping `projection`'s row/col shape for the hot path (a parent → children list instead, for tie-break only) — doesn't work, because `remove_crdt` still needs to locate a target's exact position to excise it, and keeping `projection` itself in sync on every insert (for `identities()`'s cold-path bootstrap) needs the same lookup. Real fix: a `HashMap<(IdSize, PeerIdSize), (usize, usize)>` id→position index maintained alongside `projection` on every mutation — O(1) lookup for both insert's tie-break and remove's excision, no hint, no search, ever. Might end up replacing `projection` entirely rather than just adding the index. Low priority: real typing is paced far below a synthetic full-speed burst, so processing order should stay close to send order in actual use — see [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md).
- [x] **Cut the `CRDT` middleman** (`src/shar/types.rs:34`, `src/shar/core/tree.rs` `add_crdt`) — `add_crdt` currently destructures an incoming `CRDT` into a tuple with the same fields it already has (`id, peer, value, parent, parent_peer`). Once storage moves to an id-keyed `HashMap<(IdSize, PeerIdSize), Node>`, consider making `Node` the single type used both for wire transfer and tree storage, rather than converting `CRDT` → tuple/`Node` on every insert. `Node` would be a superset of `CRDT`'s fields plus local-only bookkeeping (child/sibling pointers for O(1) sibling lookup) that never gets serialized.

## 🔴 Network — peer discovery & sync

- [ ] **UDP discovery broadcast should target the actual local/subnet-directed broadcast address, not just `255.255.255.255`** (`main.rs`) — on a machine with multiple active network interfaces at once (WiFi + Ethernet + VPN, common on e.g. a college campus), sending to `255.255.255.255` through a socket that isn't bound to a specific interface can be ambiguous about which interface it actually goes out on. The `local_ip_address` crate can get the real interface IP to compute the subnet-directed broadcast address instead, which forces the packet out the correct interface. Deferred for now — fiddly to wire into `send_to`, not blocking anything yet.
- [ ] **Petname → gossip `TopicId` derivation is deterministic but guessable** (`main.rs`) — the topic id is just the session's 3-word petname, truncated/padded to 32 bytes. Small word list means a stranger could brute-force/guess a live session's petname and join its gossip topic uninvited. Needs a more secure way to derive or share the topic id.
- [ ] **Networking setup leans on `.expect()` everywhere** (`main.rs` — endpoint bind, gossip spawn/subscribe, router shutdown, etc.) — a real network failure (bind conflict, unreachable relay, dropped connection) currently panics the whole task instead of being handled/recovered from. Needs actual error handling on the networking path instead of unwrapping/expecting success.
- [ ] **Nothing captures a connecting peer's public key anywhere** (`main.rs`'s `Event::NeighborUp(_msg)` discards its payload entirely). `state_request.rs`'s `accept`/`request_state` now log `connection.remote_id()` for debugging, but that's just a log line -- still no actual decision on what it's for (an in-memory "who's in this session" set, pushing into the discovery DB to keep its registered peer list fresh, or something else), and `ProtocolHandler::accept`'s fixed `Result<(), AcceptError>` signature still means there's no clean way to return it out of there.
- [ ] **No way to deregister a session from the discovery DB on termination** — sessions currently just sit until Upstash's 24h TTL (`EX 86400` in `shario-discovery-proxy`) expires naturally, even after the creator's process has long exited. `shario-discovery-proxy/src/index.js` only has `POST`/`PUT`/`GET` on `/sessions/:name` -- no `DELETE`. Only `create` mode ever registers a name (`main.rs`'s `SharCommands::Create` branch, via `POST`); `participate` only looks one up (`GET`) and never owns it, so only the creator's process should ever deregister, never a participant. The only existing shutdown path (`main.rs:320`'s `router.shutdown()`) only runs when the local IDE disconnects and the broadcast loop's `rx` closes naturally -- it doesn't fire on Ctrl+C/`kill`/external termination, and doesn't touch the discovery proxy at all today. Open question (2026-10-14, not yet decided): should deregistration only happen on that existing graceful path, or also on external termination (would need a `tokio::signal::ctrl_c`/`SIGTERM` handler running the same cleanup before exit)?
